# 前后端框架渐进改造方案

## 1. 目标与结论

本次改造的目标是降低前端手工 DOM 状态同步和后端组合根持续膨胀带来的维护成本，同时保持线上行为、部署形态和既有协议不变。

推荐目标形态：

- 前端采用 Vue 3 + Vite，按功能域渐进迁移。
- 后端继续保持模块化单体，候选 HTTP 框架为 Fastify。
- PostgreSQL、现有仓储、BullMQ、文档 Worker、Playwright 导出链路保持不变。
- 在迁移完成前，原生页面和原生 HTTP 路由始终是可用回退路径。

该方案不是一次性重写。任何阶段都必须做到可单独发布、可验证、可回滚。

## 2. 不可破坏的兼容边界

以下内容视为迁移合同，除非单独提出并批准破坏性变更，否则不得改变：

1. 所有现有 URL、HTTP 方法、状态码及 `{ error: string }` 错误结构。
2. 登录 Cookie、CSRF、限流、安全响应头、权限判断和 `ownerId` 数据隔离语义。
3. 简历草稿 JSON 结构、版本记录、模板 slug、模板版本号及导入导出格式。
4. 现有 DOM `id`、`data-action`、ARIA 属性、事件委托和自动化测试依赖的标记。
5. `public/core.mjs`、模板渲染、打印页面与 Worker 使用的浏览器兼容模块契约。
6. 单 Web 服务加单文档 Worker 的部署拓扑，以及现有环境变量名称。
7. 桌面端、窄屏、明暗主题和主要键盘操作行为。

迁移期间不得让 Vue 运行时进入打印文档或文档 Worker 的关键渲染路径。确定性的简历标记生成应继续由无 UI 状态的纯模块负责。

## 3. 目标架构

### 3.1 前端

```text
public/
  api-client.mjs                 # 保留：统一响应解释
  resume-api.mjs                 # 保留：简历协议
  admin-api.mjs                  # 保留：管理协议
  core.mjs                       # 保留：纯领域与数据转换
  resume-renderer.mjs            # 保留：确定性渲染
  legacy/                        # 迁移后尚未替换的原生功能
  features/
    admin/                       # 第一批 Vue 功能域
    account/
    templates/
    editor/                      # 最后一批迁移
  vue/
    bootstrap.mjs                # 局部挂载和开关判断
    shared/                      # 无业务状态组件/composable
frontend/                        # Vite 源码与构建配置
  entries/                       # 按功能域生成独立入口
  components/
  composables/
```

原则：

- Vue 组件只通过已有 API 模块访问后端，不直接调用 `fetch`。
- 领域状态按功能域拥有；跨域数据通过参数、返回值、事件或显式 store 交换。
- 初期只使用 Vue Composition API；只有出现多个独立页面共享的可变客户端状态时才引入 Pinia。
- Vite 只负责前端资源构建，不接管 Node 服务、API 代理或生产服务生命周期。
- 生产构建产物写入独立目录，例如 `public/assets/app/`，由现有静态文件服务提供。

### 3.2 后端

```text
server.mjs                       # 组合根和生命周期
server/app.mjs                   # 可选：创建应用和注册插件
server/routes/<domain>.mjs       # 鉴权、解析、服务调用、响应
server/services/<domain>.mjs     # 领域编排（按需建立）
server/*.mjs                     # 现有服务与仓储继续保留
server/http.mjs                  # 框架无关的通用 HTTP 能力
server/adapters/
  node-http.mjs                  # 原生 HTTP 适配器（迁移期）
  fastify.mjs                    # Fastify 适配器（验证后启用）
```

路由工厂继续显式接收依赖。领域服务不得依赖 Fastify 的 request/reply 对象；这样同一领域路由可以先由原生适配器调用，再切换到 Fastify。

## 4. 双轨兼容机制

### 4.1 前端局部挂载

每次只选择一个完整页面或功能域作为 Vue 挂载点。未迁移区域仍由 `public/app.mjs` 管理，两套实现不得同时拥有同一 DOM 子树。

功能开关建议采用服务端配置或构建期常量：

- `vue_admin_enabled`
- `vue_account_enabled`
- `vue_templates_enabled`
- `vue_editor_enabled`

开关关闭时加载原实现；打开时只激活对应 Vue 入口。首个试点阶段保留快速关闭开关的能力。不得因开关不同返回不同 API 协议。

### 4.2 后端适配

先把业务分支迁出 `server.mjs`，再考虑引入 Fastify。路由模块应暴露框架无关的领域处理函数，原生 HTTP 和 Fastify 适配层只负责：

- 路径参数和查询参数映射；
- 请求体读取；
- Cookie/header 映射；
- 将领域结果转换为 HTTP 响应；
- 将错误转换为既有状态码和 `{ error }`。

Fastify 接入初期必须位于功能开关之后，或者先在测试中创建第二套应用实例执行合同测试，不直接替换生产入口。

## 5. 分阶段实施

### 阶段 0：建立行为基线

交付物：

- 形成 API 合同清单：路径、方法、鉴权、输入、成功响应、错误响应。
- 为关键 API 增加黑盒合同测试，测试只依赖 HTTP 行为，不依赖内部实现。
- 为登录、创建草稿、编辑保存、模板切换、AI 建议、导出和管理操作增加 Playwright 冒烟路径。
- 保存桌面、窄屏和明暗主题的关键页面视觉基线。
- 记录当前构建体积、启动时间和关键交互性能作为对比基线。

退出条件：现有完整测试稳定通过，关键路径具备自动化保护。没有这一步，不开始框架替换。

### 阶段 1：继续收缩后端组合根

建议迁移顺序：

1. 管理端只读接口与指标。
2. 公告、消息、反馈和支持图片。
3. AI 配置、日志、任务和目标分析。
4. 导出、预览和文件下载。
5. 剩余认证接口及静态资源处理。

每个领域单独提交，保持 `server.mjs` 只进行依赖装配、全局安全策略、路由注册和生命周期管理。此阶段不引入 Fastify，避免同时改变代码位置和 HTTP 运行机制。

退出条件：`server.mjs` 不再包含大段领域路由，所有领域路由均有直接测试。

### 阶段 2：建立前端构建旁路

交付物：

- 增加 Vue 3、Vite 和独立前端构建脚本。
- 开发模式由 Vite 输出资源或提供受控开发服务；Node API 仍运行在原端口。
- 生产镜像采用多阶段构建，最终运行镜像仍只安装生产依赖并由 `server.mjs` 启动。
- 未启用 Vue 功能时，构建产物不改变现有页面行为。

建议脚本：

```json
{
  "dev:web": "vite",
  "build:web": "vite build",
  "check:web": "vite build",
  "test:e2e": "playwright test"
}
```

具体目录和命令应在实施该阶段时结合开发环境确认，不能只添加依赖而没有生产构建与 Docker 验证。

退出条件：空的 Vue 试验入口可构建、可由现有服务器提供，关闭开关后页面输出与当前版本一致。

### 阶段 3：迁移管理后台

管理后台是首选试点，因为它与简历画布和打印渲染耦合较低。

- 复用 `public/admin-api.mjs`。
- 保留现有管理页面 URL、表单字段名称、控件 ID、ARIA 与权限行为。
- 按 users、resumes、AI config、audit、recycle、templates、feedback 拆分子功能。
- 首次上线仅对管理员或内部环境启用开关。

退出条件：管理端 API 合同测试、权限测试、桌面/窄屏操作和完整测试均通过，可通过单一开关恢复原实现。

### 阶段 4：迁移账户与模板库

- 迁移登录、注册、验证码、设置和密码修改页面。
- 迁移首页草稿列表、模板目录和模板详情交互。
- 继续复用现有路由解析和 API 模块。
- 安全相关流程必须覆盖 Cookie、CSRF、验证码、限流和未登录跳转测试。

退出条件：新旧实现在相同输入下产生相同 API 请求和用户可见结果。

### 阶段 5：迁移核心编辑器

核心编辑器按能力拆分，不按视觉区域机械拆分：

1. `useResumeDocument`：规范化、模板迁移和字段操作。
2. `useHistory`：撤销、重做和变更批次。
3. `useDraftPersistence`：自动保存、冲突和修订号。
4. `usePagination`：页面高度、分页与预览刷新。
5. `useEditorSelection`：当前模块、字段和抽屉状态。
6. `useAiProposal`：AI 请求、建议选择、应用和恢复。
7. `useImportExport`：备份、Word 导入和导出任务。

`core.mjs` 和 `resume-renderer.mjs` 中可测试的纯逻辑优先原样复用。Vue 只管理交互状态和视图，不重新实现简历规范化或导出规则。

迁移可按编辑器子能力启用，但同一份简历状态只能有一个权威拥有者。过渡期使用显式适配器同步一次，不允许 Vue reactive state 与原模块级变量长期双向同步。

退出条件：草稿往返序列化结果一致，打印/导出快照一致，编辑、拖拽、历史记录、模板切换、AI 和移动端路径通过。

### 阶段 6：评估并接入 Fastify

仅在阶段 1 完成后执行：

1. 使用同一批依赖创建 Fastify 应用工厂。
2. 注册全局安全策略，逐项对比当前 header 和错误行为。
3. 将已拆分路由通过适配器注册到 Fastify。
4. 对原生与 Fastify 两套服务器运行同一组 API 合同测试。
5. 在测试/预发布环境切换入口并观察。
6. 验证稳定后才移除原生 HTTP 适配器。

如果 Fastify 只减少少量路由样板、却需要大量兼容适配，则停止在阶段 1 的模块化原生 HTTP 形态也是有效结果，不应为了技术统一强行切换。

## 6. 测试与发布门禁

每个迁移批次至少执行：

```powershell
node --check <所有变更的 .mjs 文件>
npm test
git diff --check
```

按改动范围补充：

```powershell
npm run verify:export
npm run verify:templates
npm run build:web
npm run test:e2e
```

前端批次必须人工或自动检查：

- 桌面宽屏和窄屏；
- 明色和暗色主题；
- 键盘焦点与屏幕阅读器名称；
- 登录失效、网络错误和保存冲突；
- 首屏、编辑、保存、撤销、模板切换与导出。

API 批次必须检查：

- 正常、未登录、无权限、输入错误、限流和服务异常；
- 状态码、响应 JSON 和安全 header；
- ownerId 隔离和管理员权限；
- Cookie、CSRF 与代理/HTTPS 场景。

任何阶段出现合同差异时，优先回退该功能开关或入口，不允许通过删除测试、放宽断言或同时修改客户端规避。

## 7. 提交、发布与回滚策略

- 一个提交只迁移一个领域或建立一种基础设施能力。
- 结构搬迁和行为优化分开提交；先做到行为等价，再优化内部设计。
- 数据库迁移不是框架迁移的组成部分；若确有需要，单独评审和发布。
- 前端每个功能域保留旧实现至少经过一个稳定观察周期。
- 发布顺序采用内部环境、少量开关启用、扩大启用、默认启用、删除旧实现。
- 回滚只切换功能开关或恢复服务器入口，不依赖数据库回滚。

## 8. 工作量与优先级建议

建议先完成阶段 0 和阶段 1，它们风险最低且无论是否最终采用框架都有长期价值。随后用管理后台验证 Vue 架构，再决定是否继续迁移核心编辑器。

优先级如下：

| 优先级 | 工作 | 原因 |
| --- | --- | --- |
| P0 | 合同测试与关键 E2E | 为“不影响现有功能”提供可验证依据 |
| P0 | 后端领域路由拆分 | 降低组合根风险，为 Fastify 铺路 |
| P1 | Vue/Vite 构建旁路 | 建立不接管旧页面的迁移基础 |
| P1 | 管理后台 Vue 试点 | 风险较低、能验证组件和 API 边界 |
| P2 | 账户和模板库迁移 | 扩大验证范围，仍避开核心画布 |
| P2 | 核心编辑器迁移 | 收益最大，但回归风险最高 |
| P3 | Fastify 切换 | 在路由边界稳定后再判断实际收益 |

## 9. 完成标准

框架改造只有同时满足以下条件才算完成：

1. 既有 URL、JSON、草稿、模板和 DOM 兼容合同全部通过。
2. `public/app.mjs` 与 `server.mjs` 回归组合根职责，不再承载完整业务域。
3. Vue 功能按领域隔离，API 调用仍集中在对应 API 模块。
4. 后端路由显式注入依赖，领域服务不依赖具体 HTTP 框架。
5. 全量测试、导出/模板验证和关键 E2E 通过。
6. 生产 Docker 构建、启动、健康检查、Worker 和静态资源缓存验证通过。
7. 旧实现只在新实现经过稳定观察后按领域删除，且删除不改变外部协议。
